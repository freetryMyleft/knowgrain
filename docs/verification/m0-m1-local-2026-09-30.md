# Local M0 and M1 verification — 2026-09-30

## Environment and scope

This is an isolated acceptance run on macOS using synthetic Markdown/TXT fixtures, not private user documents. The host lacked a usable Docker daemon/Compose and an installed pgvector extension. PostgreSQL 16.14 and pgvector 0.8.1 were therefore built under a temporary directory, without changing host PostgreSQL configuration. This does not verify the PostgreSQL 18 Compose deployment.

## M0 real model and storage result

With the acceptance PostgreSQL settings and cached tokenizer, `uv run --locked knowgrain` completed successfully. `ainsert -> aquery_data` returned 10 entities, 6 relationships, 1 text chunk and 1 reference.

The CLI finalized all 12 storages and closed the PostgreSQL connection pool. Temporary diagnostic artifacts are `demo-output.json` and `demo.log` beneath the runtime root; they are not repository data. The CLI fixture is synthetic and does not stand in for the M1 Vault-original workflow.

Entity descriptions are derived model output and may contain mistakes. The retrieval result proves the pipeline runs, not that generated claims are accurate. Upstream reference filenames can be reduced to basenames; M3/M4 must resolve chunk-to-document-to-revision mappings and verify original text.

## M1 actual API and browser workflow

1. Started the API with an intentionally missing LLM model. Readiness returned 503 while application database and Vault remained usable.
2. Uploaded `acceptance-source.md` through the Web page; its original was persisted and an index job queued.
3. Used “上传新修订” for `updated-source.md`; source identity stayed unchanged and the old original remained.
4. Used top-level “导入资料” for `another-source.txt`; this created a second source rather than updating the selected source.
5. Stopped the degraded API cleanly and restarted with the real models. The single embedded Core processed queued jobs.
6. Repeated the updated Markdown upload; the existing revision/job were reused.
7. At final verification, `/api/v1/health/ready` returned ready for every component. Both sources had `latest_revision_id == current_revision_id`, and the independent TXT job was `succeeded` after one attempt.

## Limits and next work

- Vault currently comes from `VAULT_ROOT`; complete Web installation/selection and safe database binding are still pending.
- Wiki generation/editing, questions, citation accuracy, Obsidian conflicts, backups and release packaging are not accepted by this run.
- No third-party model service was used; those adapters are not yet implemented.
- PostgreSQL 18 Compose and a clean-machine installation remain unverified.
- Temporary runtime files, model caches, database directories and frontend build artifacts are not committed. Keeping this preview alive is temporary; durable installation follows README configuration rather than these acceptance paths.
